# Spec: Correções para alinhamento com a filosofia v0.1

## Objetivo

Tornar o código compatível com a filosofia documentada (docs/v0.1-contract.md): robustez operacional, rastreabilidade (run_id), validação de contratos de entrada e sanitização configurável.

## Escopo

- Correções de validação de `EtlRunConfig` e normalização de campos.
- Garantir correlação de erros com `run_id` em todas as regiões que embrulham exceções.
- Expor e integrar sanitização dirigida por metadata de `StructField`.
- Adicionar testes unitários e de integração mínima para evitar regressões.
- Atualizar docs e orquestrador para garantir inputs corretos.

## Requisitos

- `run_id` deve estar presente ao empacotar/emitir erros de etapa.
- `extra_columns_policy` aceita apenas valores documentados e falha com mensagem clara quando inválido.
- Sanitização por metadata deve permitir níveis (`none`, `partial`, `full`) sem quebrar logs existentes.
- Ops devem poder diagnosticar falhas (logs com pipeline_name e run_id).
- Produção lida com milhões/bilhões de linhas sem acionar ações caras desnecessárias por padrão.

## Mudanças Propostas (tarefa por tarefa)

1. Validação e normalização
   - Arquivo: `etl_framework/models/config.py`
   - O que: garantir coerção segura de `extra_columns_policy`, mensagens de erro claras.
   - Aceitação: `EtlRunConfig(...)` com `extra_columns_policy=None` falha com ValueError legível.

2. Forçar `run_id` em wrappers de erro
   - Arquivo: `etl_framework/infra/errors.py`
   - O que: tornar `run_id` parâmetro obrigatório de `ensure_stage_error`; atualizar todos os chamadores.
   - Chamadores atuais: `etl_framework/infra/decorators.py` (já passa `context.run_id`). Verificar orquestrador e usos fora dos decorators.
   - Aceitação: qualquer tentativa de envolver erro sem `run_id` levanta ValueError detectável em testes.

3. Sanitização dirigida por metadata
   - Arquivo: `etl_framework/utils/sanitization.py` (helper `sanitize_with_metadata` já esboçado)
   - O que: integrar opção para que `SchemaMetadataValidator` ou pontos que constroem mensagens de erro passem metadata relevante (e.g., field.metadata['sanitize_level']).
   - Aceitação: logs gerados por falhas de validação respeitam `sanitize_level` quando presente; comportamento atual permanece como fallback.

4. Reduzir custos de checks por padrão
   - Arquivos: `etl_framework/utils/production_checks.py`
   - O que: documentar e oferecer opções (timeout/limit/sample) e mover ações caras para funções explícitas de `*_actional` que mantenham API; tornar `assert_` funções que podem ser chamadas na fase de certificação, não automaticamente em caminhos críticos.
   - Aceitação: pipeline padrão não executa `count()` completos automaticamente; testes de performance mostram redução de custo em dataset grande (mocked).

5. Tests
   - Local: `tests/` (criar)
   - Unit: `EtlRunConfig` normalização, `ensure_stage_error` behavior, `sanitize_with_metadata` variations.
   - Integration: simular `Pipeline.run()` com decorators e garantir logs incluem `run_id` e erros são enriquecidos.

6. Orquestrador / entrypoint
   - Atualizar o arquivo de orquestração `.py` (onde `EtlRunConfig` é instanciado) para validar/normalizar inputs e sempre prover `run_id` antes de chamar pipeline.
   - Aceitação: integração local exemplificando run com `run_id` e config inválida falhando com mensagem clara.

7. Docs
   - Atualizar `docs/v0.1-contract.md` com nota sobre `run_id` obrigatório para correlacionamento e sanitization metadata.

## Migração e Rollout

1. Branch feature/adhere-v0.1
2. Implementar mudanças e testes locais
3. CS/CI: rodar suite de testes; adicionar lint
4. Deploy: merge, monitorar runs iniciais com um canary pipeline (uma pipeline non-critical)
5. Rollback: reverter merge se erros de regressão em 2 horas

## Critérios de Aceitação (Definition of Done)

- Todos os testes passam (`pytest`).
- `EtlRunConfig` aceita e valida inputs conforme spec.
- `ensure_stage_error` exige `run_id`; decorators e chamadas comuns funcionam sem erro.
- Sanitização configurável funciona e é compatível com logs existentes.
- Docs atualizadas com instruções de orquestrador.

## Estimativa (tamanho)

- Implementação + testes + docs: 2-3 dias (1 dev experiente) ou 3-5 dias com revisões e canary rollout.

## Riscos e Mitigação

- Quebrar código externo que chama `ensure_stage_error` sem `run_id`: mitigação — buscar por chamadas globais e atualizar, adicionar compat shim se necessário.
- Regressões em performance: mitigar com testes de carga simulada e flag de rollout gradual.
