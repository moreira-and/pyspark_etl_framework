# Contrato v0.1

Este documento define o que a v0.1 do `etl_framework` entrega de fato.

O objetivo e padronizar pipelines ETL em PySpark, reduzir erros estruturais e
facilitar o trabalho de desenvolvedores junior sem esconder Spark.

## Identidade

`etl_framework` e uma biblioteca interna. Ela nao e orquestrador, catalogo,
plataforma de observabilidade, motor completo de data quality nem camada
transacional de escrita.

O framework coordena o fluxo e automatiza checks estruturais. A pipeline
concreta continua responsavel por ler, transformar e escrever dados reais.

## Fluxo Oficial

```text
extract -> check -> transform -> validate -> load -> certify
```

`Pipeline.run()` coordena a sequencia:

1. preflight de configuracao
2. `Extract.run()`
3. `Transform.run()`
4. `Load.run()`

Cada contrato usa Template Method:

```text
Pipeline.run()
  -> _preflight()

Extract.run()
  -> _run_extract()
  -> _run_check()
      -> auto_check(source_struct)
      -> _custom_check()
  -> if dry_run: limit(dry_run_limit)

Transform.run()
  -> _run_transform()
  -> _run_validate()
      -> auto_validate(target_struct)
      -> _custom_validate()

Load.run()
  -> if dry_run: _run_dry_run()
  -> _run_load()
  -> _run_certify()
```

## Responsabilidades Por Etapa

| Etapa | Dono | Responsabilidade |
| --- | --- | --- |
| `extract` | Pipeline concreta | Ler a origem e retornar `DataFrame`. |
| `check` | Framework | Validar nomes e tipos contra `source_struct`. |
| `transform` | Pipeline concreta | Aplicar regras de negocio em Spark. |
| `validate` | Framework | Validar nomes, tipos e checks contra `target_struct`. |
| `load` | Pipeline concreta | Escrever no destino. |
| `certify` | Pipeline concreta | Produzir evidencia simples apos a carga. |

## Metodos Obrigatorios

Implementacoes concretas devem fornecer:

```python
Extract._extract(spark, config, context) -> DataFrame
Transform._transform(df, spark, config, context) -> DataFrame
Load._load(df, spark, config, context) -> None
```

Hooks opcionais:

```python
Extract._custom_check(df, spark, config, context) -> DataFrame
Transform._custom_validate(df, spark, config, context) -> DataFrame
Load._certify(df, spark, config, context) -> None
```

Na v0.1, esses hooks existem para regras pequenas adicionais. Eles nao devem
duplicar o check estrutural basico que o framework ja executa.

## Configuracao

`EtlRunConfig` descreve uma execucao:

- `pipeline_name`
- `target_schema`
- `target_table`
- `target_path`
- `target_key`
- `source_struct`
- `target_struct`
- `dry_run`
- `dry_run_limit`
- `dry_run_show_rows`
- `strict_schema`
- `extra_columns_policy`
- `keep_technical_columns`
- `start_window`
- `end_window`
- `write_mode`

Embora `source_struct` e `target_struct` sejam campos opcionais no modelo, a
execucao padrao da v0.1 exige ambos. Sem `source_struct` ou `target_struct`, o
preflight de `Pipeline.run()` falha antes de `_extract`.

`strict_schema` fica preservado por compatibilidade. Quando
`strict_schema=True` e `extra_columns_policy` nao foi endurecida, o framework
trata colunas extras como `warn`.

`extra_columns_policy` controla colunas extras:

- `ignore`: ignora colunas extras;
- `warn`: emite `UserWarning` e continua;
- `fail`: falha com erro de schema.

## Auto Check

`auto_check` roda em `_run_check`, depois de `_run_extract` validar que
`_extract` retornou um `DataFrame`.

Ele usa `source_struct` para validar:

- coluna obrigatoria ausente;
- tipo incompativel;
- coluna extra conforme `extra_columns_policy`.

Ele nao cria `is_valid` e nao executa acoes Spark como `count`, `collect` ou
`show`.

## Auto Validate

`auto_validate` roda em `_run_validate`, depois de `_run_transform` validar que
`_transform` retornou um `DataFrame`.

Ele usa `target_struct` para:

- validar nomes e tipos;
- executar checks SQL declarativos em `StructField.metadata["checks"]`;
- adicionar a coluna tecnica `is_valid`;
- tratar `NULL` em regra booleana como invalido;
- bloquear registros com `is_valid=False` antes do `load`;
- em falha, informar quantidade de invalidos e checks declarativos quebrados.

O caminho feliz de bloqueio de invalidos executa uma acao Spark pequena:
`df.filter(~is_valid).limit(1).count()`. Essa acao e intencional na v0.1 para
impedir que registros invalidos cheguem ao `load`. Ela nao deve ser interpretada
como certificacao de destino, contagem completa de qualidade ou garantia de
baixo custo em qualquer volume.

Quando existe pelo menos um invalido, o framework calcula diagnostico adicional
no caminho de falha: `count()` dos invalidos e summary dos checks declarativos.
Esse diagnostico nao coleta linhas de dados nem chama `show` por padrao.

Formato de check:

```python
metadata={
    "checks": [
        {
            "name": "id_required",
            "rule": "id IS NOT NULL",
            "severity": "error",
            "message": "id is required",
        }
    ]
}
```

`severity="error"` participa de `is_valid`. `severity="warning"` nao invalida o
registro.

## Limites Do Schema

`nullable=False` em `StructField` documenta intencao de schema. Ele nao bloqueia
nulos sozinho. Para bloquear nulos, declare check SQL explicito:

```python
"rule": "customer_id IS NOT NULL"
```

Por padrao, `extra_columns_policy="ignore"`. Colunas extras nao falham no
caminho normal. Use `extra_columns_policy="warn"` para alerta ou
`extra_columns_policy="fail"` para bloquear. `strict_schema=True` e legado e
equivale a warning quando a politica explicita permanece `ignore`.

## Dry Run

Com `dry_run=True`:

- o framework executa `_extract`;
- executa `auto_check`;
- aplica `df.limit(dry_run_limit)`;
- executa `_transform`;
- executa `auto_validate`;
- `Load.run()` executa `_run_dry_run`;
- pula `_load` e `_certify`;
- registra evidencia tecnica de dry-run;
- chama `show` somente se `dry_run_show_rows > 0`.

O limite ocorre depois de `_extract` e `auto_check`. Portanto `dry_run` reduz
risco de escrita, mas nao garante baixo custo de leitura.

## Load Na v0.1

`Load` existe no contrato para manter o fluxo completo, mas a v0.1 nao fornece
uma implementacao segura de load.

`Load._load` recebe o `DataFrame` retornado por `auto_validate`. Por default,
esse `DataFrame` inclui colunas tecnicas reservadas, como `is_valid`,
`etl_run_id` e timestamps tecnicos. Quando a pipeline concreta deve entregar
apenas colunas de negocio ao destino, use `keep_technical_columns=False`.

`Load._certify` e opcional na v0.1. Quando a pipeline nao precisar produzir
evidencia simples, a implementacao default nao faz nada. Quando o destino exigir
evidencia real, a pipeline concreta deve sobrescrever `_certify`.

A pipeline concreta e responsavel por:

- staging;
- escopo de overwrite;
- idempotencia;
- retry;
- rollback;
- commit atomico quando o destino permitir;
- certificacao lendo o destino real.

Qualquer `Load` que faca `append` ou `overwrite` direto deve ser tratado como
didatico ou legado ate ter revisao senior.

Antes de `dry_run=False` em uma pipeline concreta, use
[docs/operation/load-readiness-checklist.md](operation/load-readiness-checklist.md).

## Logs E Erros

O framework emite eventos tecnicos best-effort via decorators aplicados pelo runtime.
Pipelines concretas e metodos de negocio nao devem chamar logger manualmente.

O framework registra eventos com:

- `event_schema_version`;
- `pipeline_name`;
- `run_id`;
- timestamps;
- modo;
- destino declarado;
- etapa;
- status;
- nivel operacional (`info`, `warning` ou `error`);
- duracao quando aplicavel;
- metricas explicitamente preenchidas em `context.metrics`.

Erros sao embrulhados em erros gerenciados por etapa:

- `ExtractError`
- `CheckError`
- `TransformError`
- `ValidateError`
- `LoadError`
- `CertifyError`

Os eventos/logs ajudam a diagnosticar etapa e causa tecnica. Eles sao
best-effort: falhas do sink nao quebram a ETL na v0.1. Eles nao substituem
observabilidade externa, entrega garantida de eventos nem trilha regulatoria
completa.

O backend de observabilidade e plugavel por meio da porta avancada
`ObservabilitySink`, mas essa porta nao faz parte da API cotidiana de quem
implementa ETL. A documentacao do modelo fica em
[observability/logging.md](observability/logging.md).
Builders puros de metadados operacionais ficam em
`etl_framework.utils.stage_metadata`, fora dos arquivos de contrato.
Builders puros de payload estruturado ficam em
`etl_framework.utils.observability_events`.

## API Publica Esperada

A API raiz deve permanecer pequena:

- `Pipeline`
- `EtlRunConfig`
- `EtlExecutionContext`
- `Extract`
- `Transform`
- `Load`

`ObservabilityService`, `ObservabilitySink` e sinks concretos pertencem a
infraestrutura interna ou extensao avancada para mantenedores do framework.

Helpers em `etl_framework.utils` sao opcionais e devem continuar explicitos
sobre qualquer acao Spark que executem.

O modelo de custo das acoes Spark conhecidas fica em
[docs/operation/spark-cost-and-benchmark.md](operation/spark-cost-and-benchmark.md).

## Fora Do Escopo Da v0.1

Ficam fora do escopo:

- load seguro generico;
- estrategia generica de escrita;
- idempotencia automatica;
- rollback;
- transacao generica;
- quarantine persistente;
- certificacao real de destino;
- logs JSON oficiais;
- entrega garantida de eventos de observabilidade;
- integracao com ferramenta externa de observabilidade;
- producao irrestrita sem revisao senior.
