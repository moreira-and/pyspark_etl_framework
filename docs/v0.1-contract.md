# Contrato v0.1

Este documento define o que a v0.1 do `etl_framework` entrega de fato.

O objetivo e padronizar pipelines ETL em PySpark, reduzir erros estruturais e
facilitar o trabalho de desenvolvedores junior sem esconder Spark.

## Identidade

`etl_framework` e uma biblioteca interna. Ela nao e orquestrador, catalogo,
plataforma de observabilidade, motor completo de data quality nem camada
transacional de escrita.

O framework coordena o fluxo e automatiza checks estruturais. A pipeline
concreta continua responsavel por ler, transformar e escrever dados reais.

## Fluxo Oficial

```text
extract -> check -> transform -> validate -> load -> certify
```

`Pipeline.run()` coordena a sequencia:

1. `Extract.run()`
2. `Transform.run()`
3. `Load.run()`

Cada contrato usa Template Method:

```text
Extract.run()
  -> _run_extract()
  -> _run_check()
      -> auto_check(source_struct)
      -> _custom_check()

Transform.run()
  -> _run_transform()
  -> _run_validate()
      -> auto_validate(target_struct)
      -> _custom_validate()

Load.run()
  -> if dry_run: _run_dry_run()
  -> _run_load()
  -> _run_certify()
```

## Responsabilidades Por Etapa

| Etapa | Dono | Responsabilidade |
| --- | --- | --- |
| `extract` | Pipeline concreta | Ler a origem e retornar `DataFrame`. |
| `check` | Framework | Validar nomes e tipos contra `source_struct`. |
| `transform` | Pipeline concreta | Aplicar regras de negocio em Spark. |
| `validate` | Framework | Validar nomes, tipos e checks contra `target_struct`. |
| `load` | Pipeline concreta | Escrever no destino. |
| `certify` | Pipeline concreta | Produzir evidencia simples apos a carga. |

## Metodos Obrigatorios

Implementacoes concretas devem fornecer:

```python
Extract._extract(spark, config, context) -> DataFrame
Transform._transform(df, spark, config, context) -> DataFrame
Load._load(df, spark, config, context) -> None
Load._certify(df, spark, config, context) -> None
```

Hooks opcionais:

```python
Extract._custom_check(df, spark, config, context) -> DataFrame
Transform._custom_validate(df, spark, config, context) -> DataFrame
```

Na v0.1, esses hooks existem para regras pequenas adicionais ou compatibilidade.
Eles nao devem duplicar o check estrutural basico que o framework ja executa.
Os hooks legados `_check` e `_validate` ainda sao chamados pela implementacao
padrao de `_custom_check` e `_custom_validate`, mas codigo novo deve preferir os
nomes `_custom_*`.

## Configuracao

`EtlRunConfig` descreve uma execucao:

- `pipeline_name`
- `target_schema`
- `target_table`
- `target_path`
- `target_key`
- `source_struct`
- `target_struct`
- `dry_run`
- `dry_run_limit`
- `dry_run_show_rows`
- `strict_schema`
- `start_window`
- `end_window`
- `write_mode`

Embora `source_struct` e `target_struct` sejam campos opcionais no modelo, a
execucao padrao da v0.1 exige ambos. Sem `source_struct`, `auto_check` falha. Sem
`target_struct`, `auto_validate` falha.

## Auto Check

`auto_check` roda em `_run_check`, depois de `_run_extract` validar que
`_extract` retornou um `DataFrame`.

Ele usa `source_struct` para validar:

- coluna obrigatoria ausente;
- tipo incompativel;
- coluna extra apenas quando `strict_schema=True`.

Ele nao cria `is_valid` e nao executa acoes Spark como `count`, `collect` ou
`show`.

## Auto Validate

`auto_validate` roda em `_run_validate`, depois de `_run_transform` validar que
`_transform` retornou um `DataFrame`.

Ele usa `target_struct` para:

- validar nomes e tipos;
- executar checks SQL declarativos em `StructField.metadata["checks"]`;
- adicionar a coluna tecnica `is_valid`;
- tratar `NULL` em regra booleana como invalido;
- bloquear registros com `is_valid=False` antes do `load`.

O bloqueio de invalidos executa uma acao Spark pequena:
`df.filter(~is_valid).limit(1).count()`. Essa acao e intencional na v0.1 para
impedir que registros invalidos cheguem ao `load`. Ela nao deve ser interpretada
como certificacao de destino, contagem completa de qualidade ou garantia de
baixo custo em qualquer volume.

Formato de check:

```python
metadata={
    "checks": [
        {
            "name": "id_required",
            "rule": "id IS NOT NULL",
            "severity": "error",
            "message": "id is required",
        }
    ]
}
```

`severity="error"` participa de `is_valid`. `severity="warning"` nao invalida o
registro.

## Limites Do Schema

`nullable=False` em `StructField` documenta intencao de schema. Ele nao bloqueia
nulos sozinho. Para bloquear nulos, declare check SQL explicito:

```python
"rule": "customer_id IS NOT NULL"
```

Por padrao, `strict_schema=False`. Colunas extras nao falham no caminho normal.
Com `strict_schema=True`, colunas extras geram warning, nao erro.

## Dry Run

Com `dry_run=True`:

- o framework executa `_extract`;
- executa `auto_check`;
- aplica `df.limit(dry_run_limit)`;
- executa `_transform`;
- executa `auto_validate`;
- `Load.run()` executa `_run_dry_run`;
- pula `_load` e `_certify`;
- registra evidencia tecnica de dry-run;
- chama `show` somente se `dry_run_show_rows > 0`.

O limite ocorre depois de `_extract` e `auto_check`. Portanto `dry_run` reduz
risco de escrita, mas nao garante baixo custo de leitura.

## Load Na v0.1

`Load` existe no contrato para manter o fluxo completo, mas a v0.1 nao fornece
uma implementacao segura de load.

`Load._load` recebe o `DataFrame` retornado por `auto_validate`, incluindo a
coluna tecnica `is_valid`. Se o destino fisico nao aceitar colunas tecnicas, a
implementacao concreta de `Load` deve selecionar ou remover essas colunas antes
da escrita. O framework nao faz essa projecao automaticamente na v0.1.

A pipeline concreta e responsavel por:

- staging;
- escopo de overwrite;
- idempotencia;
- retry;
- rollback;
- commit atomico quando o destino permitir;
- certificacao lendo o destino real.

Qualquer `Load` que faca `append` ou `overwrite` direto deve ser tratado como
didatico ou legado ate ter revisao senior.

## Logs E Erros

O framework registra eventos tecnicos com:

- `event_schema_version`;
- `pipeline_name`;
- `run_id`;
- timestamps;
- modo;
- destino declarado;
- etapa;
- status;
- duracao quando aplicavel;
- metricas explicitamente preenchidas em `context.metrics`.

Erros sao embrulhados em erros gerenciados por etapa:

- `ExtractError`
- `CheckError`
- `TransformError`
- `ValidateError`
- `LoadError`
- `CertifyError`

Os logs ajudam a diagnosticar etapa e causa tecnica. Eles nao substituem
observabilidade externa nem trilha regulatoria completa.

## API Publica Esperada

A API raiz deve permanecer pequena:

- `Pipeline`
- `EtlRunConfig`
- `EtlExecutionContext`
- `Extract`
- `Transform`
- `Load`

Helpers em `etl_framework.utils` sao opcionais e devem continuar explicitos
sobre qualquer acao Spark que executem.

## Fora Do Escopo Da v0.1

Ficam fora do escopo:

- `SafeLoad`;
- `LoadStrategy`;
- idempotencia automatica;
- rollback;
- transacao generica;
- quarantine persistente;
- certificacao real de destino;
- logs JSON oficiais;
- integracao com ferramenta externa de observabilidade;
- producao irrestrita sem revisao senior.
